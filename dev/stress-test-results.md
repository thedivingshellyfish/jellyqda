# Stress test: jellyqda with 15, 50 and 150 interviews

*jellyqda 0.9.0, measured on 27 Nov 2026 in a Linux container (R 4.3.3,
SQLite 3.44, Chromium via Playwright). Script: [`stress_test.R`](stress_test.R),
raw numbers: [`stress-test-results.csv`](stress-test-results.csv). All
transcripts are fictional (generated by `data-raw/transcript_generator.R`).*

## Scenarios (from common study practice)

| Scenario | Typical study | Interviews | Talk | Segments (speaker turns) | Codings | Project file |
|---|---|---|---|---|---|---|
| **S** | master's thesis | 15 × 30–90 min | 15.5 h | 3,524 | 863 | 1.4 MB |
| **M** | PhD, funded project | 50 × 30–90 min | 49 h | 11,361 | 2,821 | 4.3 MB |
| **L** | large multi-site / panel study | 150 × 30–90 min | 145 h | 33,533 | 8,310 | 12.6 MB |

Code system: 8 code families × 4 subcodes (40 codes). Every coding was made
one by one with `qda_code()`, so the audit trail grows as in real work
(L: about 8,400 events). 150 interviews is at the upper end of qualitative
interview studies and serves as a real stress test.

## What we changed because of the test

The first run (before the fixes) found real bottlenecks in large projects:

| Bottleneck (L, 150 interviews) | Before | After | Fix |
|---|---|---|---|
| code a passage in the app (browser) | 1.8 s | 0.79 s | see below |
| first page in the app (browser) | 4.4 s | 2.9 s | |
| `qda_codings()` | 1.25 s | 0.03 s | text of each document loaded once instead of joined to every coding (copied > 300 MB) |
| `qda_sources()` | 0.40 s | 0.03 s | texts cached per open project (frozen = never change); segment counts in SQL |
| `qda_stats()`, coded characters | 0.2 s | 0.03 s | codings split by document once; vectorised union of intervals |
| undo/redo state, after every action | 0.18 s | < 0.01 s | walked incrementally (events are only appended) |
| document variables | 2.8 s per 10 actions | — | without loading the text; all documents in one query |
| code matrix, summary grid | 0.9 s per action | 0.2 s | built as matrices instead of cell by cell |
| "All Codings" panel | 3.6 MB HTML | 0.13 MB | first 300 rows + hint how to narrow the list |
| portraits (data + SVG) | ~2 s | 1.2 s | vectorised |

## Assessment

* **15 and 50 interviews:** everything feels immediate; coding takes well
  under half a second.
* **150 interviews:** works; coding takes 0.8 s (every 25th action about
  1.7 s because of the automatic restore point). The project file stays
  small (12.6 MB).
* **The report** with all documents takes 20 s and is 21 MB with 150
  interviews. Since 0.9.1 the app offers an **overview** without the
  documents (3.3 s, 4.2 MB with 150 interviews), shows a **progress bar**
  (62 updates during the 25 s of the complete report, measured in the
  browser) and the expected time; the estimate (25 s) matched the
  measured 24.9 s.
* **Next candidates:** keyword search and word frequencies (0.7–0.8 s at
  150 interviews) could use an index; the automatic restore point could be
  written in the background.

## How to repeat it

```r
pkgload::load_all(".")
source("dev/stress_test.R")                       # all three scenarios (~6 minutes)
options(jellyqda.stress.sizes = 15); source("dev/stress_test.R")   # only S
```

The browser numbers were measured with Playwright against `qda_app()`; the
script measures the app server side via `shiny::testServer()`, which also
recomputes the outputs of closed windows and therefore shows higher values
for "one coding" than a real browser.
